# ServerLens Architecture

## Current System

ServerLens is a local-first Node.js web app with a static frontend, small HTTP API, SQLite persistence, and an Electron desktop shell.

## Runtime Units

- `src/server/index.js`: starts the local HTTP server and persists to `data/serverlens.sqlite` unless `SERVERLENS_DB_PATH` is set.
- `src/server/app.js`: routes API requests and serves frontend assets.
- `src/server/store.js`: in-memory or SQLite-backed server, snapshot, append-only snapshot history, report, analysis job, local alert, and settings storage.
- `src/server/collector.js`: normalizes telemetry, provides local demo snapshots, and can collect authorized SSH agent/key telemetry including disk IO/iowait and passive established connection summaries through the system `ssh` command.
- `src/shared/analysis-engine.js`: rule-based health, security, runtime, ecosystem, logs, network, and performance findings with defensive diagnostic commands, local executive summaries, redacted evidence appendices, and report remediation checklists.
- `src/shared/delivery-evidence.js`: shared local handoff manifest, readiness gate, UI audit, package checklist, and command-level validation ledger builder used by API and packaging scripts.
- `public/`: macOS-style operator interface. `public/app.js` is the runtime entry (loaded as an ES module); DOM-free logic is extracted into `public/js/` modules (`format.js`, `commands.js`, `page-model.js`) for direct unit testing. No build/bundling step is required — the browser loads native ES modules.
- `src/desktop/main.cjs`: Electron shell that stores `serverlens.sqlite` in Electron userData and opens the local app server in a native window.
- `scripts/create-handoff-package.js`: assembles the offline delivery directory after desktop packaging.
- `scripts/delivery-validate.js`: runs the local commercial validation sequence and writes command-level `delivery-validation.json` ledgers.
- `scripts/ui-visual-evidence.js`: captures local desktop/mobile browser screenshots and layout evidence through Playwright, including installed system Chrome fallback when bundled Playwright Chromium is unavailable, or writes a blocked evidence JSON when browser automation is unavailable.
- `scripts/runtime-smoke.js`: starts the local API and verifies UI runtime contracts through hidden Electron rendering when available, with an explicit static fallback for host sessions where Electron `loadURL` is unavailable.

## Data Flow

1. User adds, edits, archives, restores, or selects a server.
2. API normalizes server asset metadata: host, port, auth type, group, tags, and connection-test state.
3. Server edits reuse the same validation path and reset connection-test state when endpoint or authentication metadata changes.
4. Server archive/restore changes only lifecycle state. Archived servers stay in SQLite for audit/detail/report review, are excluded from the default operational server list, and must be restored before connection testing, collection, or analysis.
5. Inventory transfer calls `/api/servers/export` and `/api/servers/import` for sanitized metadata-only JSON migration. The format excludes passwords, snapshots, reports, alerts, logs, and telemetry payloads.
6. User can run an explicit connection test. Demo assets are skipped without opening external connections; non-demo assets use short TCP reachability checks for the configured endpoint.
7. API collects a snapshot through the demo/local collector, or through explicit SSH mode for configured servers using BatchMode agent/key authentication and passive local telemetry commands such as `ss`.
8. User selects target server, analysis preset or custom modules, time range, analysis depth, and output behavior.
9. API resolves presets into modules/depth/time range, creates an analysis job with the resolved scope, and runs the analysis engine with local settings thresholds.
10. Analysis engine generates evidence-backed findings, resolved analysis scope, diagnostic commands, risk event timeline, security source review, redacted evidence appendix, service topology, service catalog, trends, recommendations, report remediation checklist, optional local executive summary, and a bounded health score.
11. Service topology links the server to observed services, listening ports, containers, and topology-specific risks from the same authorized snapshot.
12. Service Catalog groups observed services, listeners, containers, and matching findings into operator roles, health, exposure, backing owners, risks, and recommendations without active discovery.
13. Service Topology Map derives stable local layout data from the same topology nodes, edges, and risks so the UI can render a compact service/port/container map without external graph services.
14. Server Detail renders runtime inventory panels from the latest snapshot: containers, listening ports, and firewall posture with public/high-risk port evidence.
15. Store creates local alert inbox entries for findings matching configured severities, defaulting to critical and high.
16. Frontend renders dashboard metrics, ranking table, alerts, server detail, performance charts, security events, security source review, topology map/list, service catalog, runtime inventory, task history, findings, settings, alert inbox, delivery evidence, delivery readiness, handoff checklist, report details, and a Command Center for quick operator actions.
17. Alert Inbox calls `/api/alerts`; users can acknowledge items through `/api/alerts/:id/ack`, and acknowledgement state persists in SQLite.
18. Reports Center calls `/api/reports/summary` to render historical reports, score/finding trends, and current-vs-previous comparison. A selected history row calls `/api/reports/:id` and keeps the chosen report focused in the UI.
19. Status Page Preview calls `/api/status-page` to render a redacted local service status and incident summary for handoff review without hostnames, SSH metadata, connection state, snapshots, or raw telemetry.
20. Reports can be exported as Markdown through `/api/reports/:id/markdown`, including topology map summary, risk event timeline, security source review, evidence appendix, remediation checklist, service catalog, service topology, and finding-level command sections.
21. Reports can be opened through `/api/reports/:id/print` as print-ready HTML for browser or desktop "Save as PDF" handoff, including topology map summary, risk event timeline, security source review, evidence appendix, remediation checklist, service catalog, and finding-level command blocks.
22. Server runbooks can be exported as Markdown through `/api/servers/:id/runbook/markdown`, combining asset metadata, latest snapshot, latest report, topology map summary, service catalog, risk event timeline, security source review, evidence appendix, remediation checklist, diagnostic commands, and safety boundary notes.
23. Retention Maintenance calls `/api/maintenance/retention` to delete expired report, analysis job, local alert, and snapshot history using the configured retention window, while preserving each server's latest report and current snapshot.
23a. Snapshot collection appends each snapshot to an append-only `snapshot_history` table per server. Analysis trends are computed from this real history; when fewer than three snapshots exist, trends carry the real points collected so far and an explicit `insufficient-history` status instead of any synthetic curve.
24. Delivery Evidence calls `/api/delivery/evidence` to expose a local handoff manifest with package path, verification commands, local GitHub reference names, implemented capabilities, and safety boundaries.
25. Delivery Readiness calls `/api/delivery/readiness` to expose categorized local pass/fail checks for verification commands, packaging, GitHub references, safety boundaries, commercial capabilities, and product UI contracts.
26. UI Experience Audit calls `/api/delivery/ui-audit` to expose local material, scrolling, control, responsive, and runtime-smoke evidence for commercial design review.
27. Handoff Checklist calls `/api/delivery/checklist` to derive first-run client review steps from local servers, latest report, export routes, readiness status, packaging commands, UI experience audit, and safety boundary evidence. Offline package checklists also include delivery-validation review status when a validation ledger is available.
28. Strategy Iteration Workspace calls `/api/delivery/strategy` to expose ten ServerLens 9.0 planning cycles, each with plan, execution, validation, evidence, reference basis, and package handoff context.
29. UI Visual Evidence runs `npm.cmd run ui:evidence` to start the local app, capture desktop/mobile screenshots through Playwright or installed system Chrome via Playwright, fall back to Electron rendering, then fall back to installed Edge/Chrome system-browser capture, and write `dist/ui-visual-evidence.json`; when this host cannot render screenshots it writes a blocked reason instead of a false screenshot claim.
30. Delivery Validation runs `npm.cmd test`, `npm.cmd run build`, `npm.cmd run runtime:smoke`, `npm.cmd run ui:evidence`, `npm.cmd run package:app`, and `npm.cmd run handoff:dir`, then writes `dist/delivery-validation.json` plus the handoff copy. If UI visual evidence writes `status: blocked`, the ledger records that command as `warn` and the overall ledger as `review`.
31. Runtime Smoke starts an in-memory local app, attempts hidden Electron rendering, checks Readiness Gate and Command Center behavior, and falls back to local API/HTML/CSS/JS contract verification when the host blocks Electron `loadURL`.
32. With a configured database path, servers, snapshots, reports, analysis jobs, local alerts, and settings survive process restarts without re-seeding duplicate demo servers.

## Frontend Constraints

- Register: product UI. The interface serves repeated operator work, so density, stable navigation, fixed typography, and clear controls are preferred over hero-style composition.
- Material: ServerLens 6.0 uses a shadcn + Konsta product system with calm iOS surfaces, 1px hairlines, grouped panels, native-feeling controls, and compact workbench spacing.
- Motion and scrolling: page/view transitions use short ease-out motion, while Reports Center uses local scroll containers with touch-friendly momentum and contained overscroll.
- iOS/Konsta interaction layer: command surfaces use subtle pressed states, badges, toolbars, meters, fields, inputs, selects, segments, grouped panels, and sheet states. Feedback and navigation affordances do not execute hidden server actions.
- Asset operation: server inventory supports inline add/edit plus reversible archive/restore. The default fleet view hides archived assets, while the Show archived toggle keeps retired assets available for audit.
- Inventory transfer operation: server inventory includes compact JSON export/import controls. Import reuses server metadata validation, skips duplicate name/host/port assets, and preserves archive state.
- Analysis operation: target server and time range are explicit selects, depth controls are real segmented buttons, preset controls offer Full Report, Security Review, Runtime Health, Service Ecosystem, and Custom scopes, and output behavior can keep the user on the page, copy Markdown, or open the print-ready PDF route after a run.
- Remediation operation: report detail renders a local Remediation Checklist after the executive summary. It groups finding-derived actions into contain, stabilize, investigate, and prevent phases with owner hints, evidence, diagnostic commands, and acceptance criteria.
- Status operation: Reports Center includes a local Status Page Preview and Command Center refresh action. It summarizes grouped service status and unacknowledged incidents but deliberately redacts endpoint, credential, connection, and telemetry fields.
- Runtime operation: server detail separates topology from raw runtime inventory so operators can inspect Docker/container status, bound ports, and firewall posture without reading report prose first.
- Topology operation: server detail renders a compact local Service Topology Map before the edge list, using stable analysis-engine layout data for server, service, port, and container nodes.
- Service operation: server detail includes a Service Catalog list for roles, health, exposure, backing owner, top risk, and recommendation so operators can scan the service ecosystem before reading raw ports or containers.
- Performance operation: server detail includes compact CPU, memory, disk capacity, disk IO, and network chart cards with pressure meters for quick repeated scanning.
- Security operation: server detail shows evidence-backed security events and a local Risk Event Timeline from collected telemetry, including SSH failures, auth failures, high-risk exposed ports, unknown public listener ownership, error-log pressure, and repeated remote connections. The timeline is a review sequence, not an attribution or response engine.
- Security source operation: server detail and report surfaces include a local Security Source Review from collected authentication counts and repeated connection records. SSH collection populates repeated connection records from passive established-connection summaries. The review summarizes source labels, ports, signals, evidence, and review actions without attribution, IP enrichment, blocking, scanning, or remote modification.
- Evidence operation: server detail and report surfaces include a redacted Evidence Appendix with finding IDs, source modules, evidence summaries, diagnostic commands, and a clear redaction policy for handoff review.
- Navigation operation: the top search control and Ctrl/Cmd+K open a Command Center that filters commands locally and can navigate, open server detail, collect telemetry, run analysis, copy Markdown, or open PDF handoff for the current report.
- Delivery Workspace operation (14.0): the former separate Inspection, Release, and Strategy views are consolidated into a single `delivery-view` with an Inspect / Validate / Handoff tab bar. The three panels keep their original DOM ids, render functions, and `/api/delivery/*` data sources; only navigation is folded into one nav entry and three tabs. Existing commands and page-experience actions that target the old view names are routed to the matching delivery tab.
- Responsive operation: the fleet health ranking keeps the desktop table structure for wide layouts and switches to labeled compact rows on mobile so score, CPU, memory, and disk values remain scannable without horizontal overflow.
- Collection operation: SSH mode requires an explicit server asset and uses host, port, optional username, and optional key path. Password collection is rejected because the app does not store secrets in this delivery build.
- Settings operation: threshold, retention, local-only notification, alert inbox, alert severity rules, and AI summary flags are persisted through the same local settings API and SQLite store. When AI summary is enabled, reports include a local rule-generated executive summary; no external AI service is called. Operators can run Retention Maintenance from Settings or Command Center for an explicit local cleanup pass.
- Handoff operation: Settings includes Delivery Evidence, Readiness Gate, and Handoff Checklist panels that load local manifest, pre-handoff checks, and first-run client review steps without external calls or sensitive telemetry. Command Center can open the readiness gate and checklist directly.
- Strategy operation: the app shell includes a Strategy Workspace for the ServerLens 9.0 major-version cycle. It renders ten strategy cards, a plan/execution/validation/evidence panel, reference summary, copy feedback, and Command Center/Action Dock routes without external calls, hidden collection, server changes, or release command execution.
- v6.0 design operation: the shell uses `v6-ios-shell`, `ios-toolbar`, `ios-badge`, `ios-panel`, `ios-list`, `ios-meter`, `ios-field`, `ios-input`, `ios-select`, `ios-button`, and `ios-segment` contracts while preserving explicit button activation.
- UI experience operation: Settings includes a UI Experience Audit panel and Command Center action that summarize ServerLens 6.0 material, OKLCH tokens, contained touch scrolling, control states, responsive structure, and runtime-smoke evidence without external calls or telemetry access.
- Runbook operation: Reports Center includes an Export Runbook button and Command Center action that copies the active server runbook Markdown for client handoff and operator onboarding, including the latest risk event timeline and evidence appendix when a report exists.
- Packaging operation: `npm.cmd run handoff:dir` copies `dist/win-unpacked` or the controlled `SERVERLENS_HANDOFF_APP_DIR`, docs, CodeStable architecture/features/roadmap, Strategy Workspace evidence, `delivery-evidence.json` with readiness status, UI visual evidence status, validation ledger status, and offline handoff checklist, `delivery-validation.json` with command-level validation ledger structure, optional `ui-visual-evidence.json` and `ui-evidence` screenshots, and `START-HERE.txt` into `dist/handoff/ServerLens-{version}`. `npm.cmd run delivery:validate` runs the commercial validation sequence and refreshes both source and handoff validation ledgers plus the offline package checklist; screenshot evidence blockers are represented as `review` warnings rather than hidden behind a ready ledger. `SERVERLENS_PACKAGE_DIR` can redirect package output inside `dist` when Windows locks the default packaged app directory.
- Build guardrails reject pure black/white, gradient text, side-stripe card accents, and viewport-scaled typography.

## Delivery Boundary

The current build is suitable for local commercial demo delivery and packaged desktop handoff. It includes packaged desktop distribution, SQLite-backed local persistence, authorized SSH agent/key collection, risk event timeline exports, redacted evidence appendix exports, first-run handoff checklist, ServerLens 9.0 Strategy Iteration Workspace, RetroUI Card Clarity, and local alert acknowledgement workflow. As of 11.0 the local API binds to loopback (`127.0.0.1`) by default with an optional `SERVERLENS_API_TOKEN` gate on write operations, identifiers use `node:crypto`, and SSH credential metadata can be stored as an AES-256-GCM envelope when `SERVERLENS_CRED_KEY` is set (default off). As of 15.0 the delivery surface is reachable via accessibility affordances (skip link, ARIA tab set, live regions, `aria-current` navigation, reduced-motion support), an optional outbound alert webhook can be enabled (default off, double-gated by `localOnly=false` and `webhook.enabled`, https-only, redacted metadata only), and optional Windows Authenticode signing runs during packaging when a certificate is supplied (default falls back to the unsigned `dir` target). As of 16.0 a real-time fleet Ecosystem overview (`/api/ecosystem/overview`) aggregates resource pressure, service mix, container fleet, exposure surface, risk distribution, and live freshness trends from collected telemetry only — replacing the former decorative Experience Deck and Scenario Board. Public status pages remain a planned extension.

## Runtime Constraints

- Source-mode development requires Node `>=24.0.0` because the persistence layer uses built-in `node:sqlite`.
- The local HTTP API binds to `127.0.0.1` by default (`SERVERLENS_BIND_HOST` to override). When `SERVERLENS_API_TOKEN` is set, POST/PUT/PATCH/DELETE on `/api/*` require a matching `Authorization: Bearer` header verified with a timing-safe comparison; reads stay open for the local UI. Request bodies over 256KB are rejected. When unset, behavior is unchanged so demo mode runs with zero configuration.
- Identifiers (server, snapshot, report, analysis-job) use `node:crypto` and a monotonic counter so IDs are unique and are not reused after retention deletes.
- SSH credential metadata (`keyPath`) is stored as an AES-256-GCM envelope at rest when `SERVERLENS_CRED_KEY` is set; in-memory values stay plaintext for the collector. Without the key, plaintext metadata storage is preserved.
- Packaged desktop delivery uses Electron and stores data in the Electron userData folder.
- Security, service, and performance analysis is defensive only and is limited to authorized telemetry, logs, ports, service state, container state, disk IO/iowait, passive established connection summaries, and runtime signals. Unknown listener detection, Service Catalog, and Remediation Checklist evaluate collected records and generated findings only and do not perform hidden network discovery.
- Risk Event Timeline groups already collected local evidence into reviewable events. It does not attribute activity, enrich sources, block connections, scan adjacent hosts, or modify infrastructure.
- Evidence Appendix includes metadata and rule evidence summaries only. It excludes passwords, private keys, raw logs, secret values, and collected telemetry payloads.
- Disk IO collection uses passive host telemetry such as `iostat` and `vmstat` when available, falls back to zero when unavailable, and never runs write benchmarks or stress tests.
- Analysis presets are local scope shortcuts only. They resolve to existing modules, depth, and time range; they do not add hidden collection, active scanning, external enrichment, or external AI calls.
- Finding commands are diagnostic only and are meant for authorized inspection of the user's own systems.
- Remediation Checklist is advisory only. It does not execute commands, change remote hosts, approve risks, or modify infrastructure.
- Server Runbook export is advisory and local-only. It excludes passwords, raw secrets, and private keys, and it does not execute diagnostic commands.
- AI summary is an offline/local executive-summary generator in this delivery. No external AI service is called by default.
- Strategy Iteration Workspace is a local review artifact for release planning and handoff evidence. It does not collect telemetry, scan networks, modify servers, enrich sources, publish status pages, or execute packaging commands.
- ServerLens 6.0 shadcn + Konsta Redesign is a local UI behavior and material layer. It adds tactile component states and stronger product hierarchy to existing explicit workflows; it does not add hidden gestures that collect telemetry, run analysis, export reports, modify servers, or package releases.
- As of 15.0 an optional outbound alert webhook (planned extension) is the only path that sends data off the machine. It is double-gated and off by default: `notifications.localOnly` must be explicitly `false` AND `notifications.webhook.enabled` must be `true` with a valid `https` URL. When either gate is closed, no connection is opened. The payload carries only redacted alert metadata (id, severity, category, title) already shown in the local inbox — never raw logs, secrets, or credentials. A failed webhook never blocks local analysis.
- As of 15.0 optional Windows Authenticode signing runs during packaging only when `SERVERLENS_SIGN_CERT` is supplied. Without it, packaging falls back to the unsigned `dir` target so demo/handoff builds work with zero signing infrastructure; a signing attempt never aborts packaging.
- Accessibility (15.0): a skip link targets the main landmark, the Delivery Workspace is a real ARIA tab set (`role="tablist"`/`tab`/`tabpanel`), active navigation uses `aria-current`, dynamic status surfaces use `aria-live="polite"`, and `prefers-reduced-motion` suppresses non-essential animation.
- Ecosystem overview (16.0): the `/api/ecosystem/overview` endpoint and `buildEcosystemOverview` (`src/shared/ecosystem-overview.js`) are a pure read-only aggregation of data the store already holds (servers, latest snapshots, snapshot history, latest reports). They trigger no new collection, open no network connection, and call no external service. Fleet trends follow the 12.0 honesty contract: fewer than three aligned points are flagged `insufficient-history` rather than padded with synthetic values. The output excludes secrets — no passwords, key paths, SSH usernames, or raw telemetry payloads, only the rolled-up counts/labels the per-server views already show. This replaced the former decorative Experience Deck and Scenario Board, and removed the last simulated visualization (the live-monitor sine-wave sweep).
